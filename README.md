# NordCodes: API-тесты

Автоматизированные проверки предоставленного Spring Boot приложения. Тесты работают через HTTP с неизменённым JAR; исходники приложения и настоящие внешние сервисы не используются.

Стек: Java 17+, JUnit 5, WireMock, Allure, Maven Wrapper. Отдельная установка Maven, WireMock, Allure или Docker не требуется. При первом запуске нужен интернет для загрузки Maven и зависимостей.

## Быстрый запуск

1. Установить JDK 17 или новее; `JAVA_HOME` должен указывать на этот JDK.
2. Поместить предоставленный `internal-0.0.1-SNAPSHOT.jar` в `app/`.
3. Выполнить из корня проекта:

```powershell
# Windows PowerShell
.\mvnw.cmd --batch-mode --no-transfer-progress clean verify
```

```bash
# Linux / macOS
chmod +x mvnw
./mvnw --batch-mode --no-transfer-progress clean verify
```

Другой путь к приложению:

```powershell
.\mvnw.cmd clean verify "-Dsut.jar=C:/path/to/internal-0.0.1-SNAPSHOT.jar"
```

Приложение и WireMock запускаются автоматически на свободных локальных портах. Рабочие сервисы на `8080`/`8888` не затрагиваются. Останавливать их перед запуском тестов не требуется.

**Для предоставленной версии приложения ожидаются падения проверок допустимых токенов с буквами G-Z: это NC-001, расхождение с заданием.** Тесты не отключены, сборка возвращает ненулевой код. Это не ошибка установки проекта. Все прочие неожиданные падения нужно исследовать отдельно. Подробности: [дефекты](docs/DEFECTS.md), [результаты проверенного запуска](TEST_REPORT.md).

## Отчёты

- **`target/allure-report/summary.html` — краткий отчёт на русском.** Содержит таблицу результатов, описание найденного дефекта и раскрываемые списки сценариев. Формируется автоматически из результатов Allure.
- `target/allure-report/index.html` — отчёт Allure в одном HTML-файле. Можно открыть непосредственно в браузере и передать отдельным файлом.
- `target/allure-results/` — исходные результаты, шаги и вложения.
- `target/failsafe-reports/` — XML и текстовые результаты JUnit/Failsafe.
- `target/app-logs/` — логи запущенных экземпляров приложения.

Оба отчёта генерируются в `post-integration-test`, до итогового `failsafe:verify`. Поэтому обычные падения проверок не мешают сформировать отчёты и не скрываются успешным кодом генерации HTML. Ошибка компиляции или авария Maven до этой фазы может помешать генерации. Генератор сводки не создаёт сообщение об успехе, если результатов нет, и учитывает ошибки выполнения и пропущенные сценарии отдельно от успешных.

Повторно построить HTML из существующих результатов:

```powershell
.\mvnw.cmd allure:report exec:java
```

Для независимого нового запуска используйте `clean verify`: старые результаты удаляются вместе с `target`. Запуск без `clean` может включить в Allure результаты предыдущих запусков.

Начать можно с `summary.html`. Вверху есть ссылка на подробный Allure с запросами, ответами и журналами. Оба HTML-файла открываются с диска; передавайте их вместе в одной папке.

В Allure есть русские названия сценариев, действий и описания ожидаемого поведения. Переданные данные, ответы и журналы сохранены во вложениях. NC-001 выделен отдельной категорией с понятным описанием ошибки входа. Вложенные API-ключи заменены описанием тестового значения; токены синтетические.

## Проверяемые требования

- Доступ по корректному API-ключу, запрет всех действий без него или с неверным значением.
- Токен длиной ровно 32 символа из `A-Z0-9`: допустимые классы, границы длины, недопустимые символы, отсутствующие параметры.
- Действия LOGIN, ACTION, LOGOUT и отклонение неизвестных действий.
- Передача корректного POST, токена и заголовков во внешние `/auth` и `/doAction`.
- Сохранение авторизации, её удаление при выходе, запрет действий до входа и после выхода.
- Независимость пользователей и небольшой сценарий параллельной работы восьми сессий.
- Обработка успешных/ошибочных внешних ответов, разрыва соединения, небольшой задержки и восстановление после ошибки.
- Независимость результата от тела внешнего ответа.
- JSON-ответы, поля `result` и `message`, отсутствие внешних запросов при локальном отказе.

Связь требований и методов тестов: [матрица покрытия](docs/COVERAGE.md).

## Допущения

Задание описывает общий контракт, но не все коды и дополнительные переходы состояния. Ниже явно перечислены принятые ожидания. Они не выдаются за дословные требования работодателя. Предварительные HTTP-наблюдения использовались для проверки реализуемости этих ожиданий, а не для замены явно заданного контракта.

| ID | Принятое ожидание | Основание / граница |
| --- | --- | --- |
| A1 | Успех: HTTP 200 и `result: OK` без поля `message`. Некорректные параметры: 400; неверный/отсутствующий ключ: 401; действие без сессии: 403. Ошибка содержит непустой строковый `message`. | Формы JSON даны в задании, конкретные HTTP-коды и отсутствие `message` при успехе — допущения, подтверждённые наблюдением этой версии JAR. Тексты ошибок не сравниваются дословно и не зависят от локали. |
| A2 | Внешние ответы 2xx означают успех. | Задание не перечисляет успешные коды. Проверяются 200, 201, 202, 204, 299. Это выбор представителей класса и границ, а не перебор всех 100 кодов. |
| A3 | Внешний 4xx/5xx или разрыв соединения возвращает HTTP 500 / ERROR; неуспешный LOGIN не авторизует токен, ошибка ACTION сохраняет авторизацию. | Формат ошибки задан; точный статус и политика сохранения сессии при ошибке ACTION — допущения. После восстановления сервиса проверяется возможность продолжить работу. |
| A4 | Повторный LOGIN активного токена: 409; LOGOUT неизвестного или уже удалённого токена: 403. Оба отказа локальные. | Не описано в задании, соответствует наблюдению; явно выделено в `AdditionalBehaviorIT`. |
| A5 | Пробелы по краям `action` удаляются; неизвестные дополнительные поля игнорируются. | Дополнительное наблюдаемое поведение, не обязательная часть контракта; выделено в `AdditionalBehaviorIT`. |
| A6 | При обычном завершённом HTTP-ответе ожидается одно обращение в нужный внешний метод. При разрыве соединения число попыток не фиксируется. | Примеры задания показывают одно обращение; политика сетевых повторов не задана. |

Тайм-аут HTTP-клиента тестов (8 секунд), предел готовности приложения (40 секунд) и общий предел параллельного сценария — технические ограничения тестового стенда, не требования ко времени ответа продукта. Проверка задержки 250 мс не является проверкой продуктового тайм-аута или нагрузочным тестом. Неопределённую политику длительных ожиданий не имитируем как установленное требование.

Ответы 3xx, неподдерживаемые HTTP-методы и Content-Type описаны в [наблюдениях](docs/DEFECTS.md). Их поведение не превращено в подтверждённое требование или искусственно успешный тест.

## Устройство тестов

```text
JUnit → HTTP-клиент → предоставленный JAR → WireMock
          ↓                  ↓                 ↓
       запрос/ответ     отдельный процесс   проверка запросов
                         и лог              и ответы-заглушки
```

Тесты находятся в `src/test/java/ru/nordcodes/aqa/`:

| Класс | Назначение |
| --- | --- |
| `ApiKeyIT` | Ключ и отсутствие изменения сессии при отказе в доступе |
| `TokenValidationIT` | Токены, границы, обязательные параметры и действия |
| `SessionLifecycleIT` | Полные сценарии, изоляция и параллельные пользователи |
| `ExternalServiceIT` | Внешние коды, тела, сетевые ошибки и восстановление |
| `AdditionalBehaviorIT` | Повторные действия и явно принятые допущения A4/A5 |
| `support/` | Запуск/остановка JAR, HTTP-клиент, проверки JSON, тестовые данные |

Один новый процесс JAR и WireMock на класс. Перед каждым тестом очищаются заглушки и журнал; динамические токены не повторяются внутри JVM. Сессии не требуют общего порядка тестов. Фиксированные токены параметризованных проверок уникальны в своём классе. Накопленные сессии полностью исчезают при остановке процесса класса.

JUnit запускается последовательно, один fork Maven; только отдельный проверяемый сценарий намеренно отправляет параллельные запросы. Процессы завершаются после класса и через shutdown hook при обычном завершении JVM. Принудительное завершение всей ОС/дерева процессов не может гарантировать выполнение Java cleanup.

Используются программные шаги и вложения Allure, поэтому AspectJ/Java agent не нужен. Mockito, JaCoCo и исходники приложения не требуются. Матрица описывает функциональное покрытие; утверждений о проценте покрытия строк приложения нет.

## Запуск выбранных проверок

```powershell
# Один класс
.\mvnw.cmd clean verify "-Dit.test=SessionLifecycleIT"

# Воспроизведение NC-001: семь вариантов токена, три из них отклоняются вопреки заданию
.\mvnw.cmd clean verify "-Dit.test=TokenValidationIT#acceptsTokensFromRequiredAlphabet"
```

Полный приёмочный запуск — `clean verify` без фильтров. `mvn test` не запускает эти `*IT`: они привязаны к Maven Failsafe и фазе integration-test.

## Подключение приложения и зависимости

Предоставленный бинарный JAR не входит в исходники тестов. Путь по умолчанию — `app/internal-0.0.1-SNAPSHOT.jar`; другие пути задаются через `sut.jar`. Ссылки на само приложение приведены в выданном работодателем задании.

Maven Wrapper закреплён на Maven 3.9.16, зависимости и плагины закреплены в `pom.xml`. Команда не обращается к рабочим внешним API: весь внешний сервис заменён локальным WireMock. Проверка `sut.jar` выполняется до старта приложения и сообщает понятный путь, если файл отсутствует.

Официальные справочники: [JUnit 5](https://docs.junit.org/5.14.4/user-guide/), [WireMock](https://wiremock.org/docs/), [Allure Jupiter](https://allurereport.org/docs/junit-jupiter/), [Maven Wrapper](https://maven.apache.org/tools/wrapper/).
