# Дефекты и исследовательские наблюдения

## NC-001 — токены с разрешёнными буквами G-Z отклоняются

**Основание:** в выданном задании и `app/README.md` токен определён как строка из 32 символов A-Z0-9.

**Важность:** высокая для контракта авторизации — корректный по требованиям пользователь не может войти.

**Предусловия:** приложение запущено с корректным API-ключом; внешний POST `/auth` настроен на HTTP 200.

**Шаги:** отправить POST `/endpoint` с корректным `X-Api-Key`, Content-Type `application/x-www-form-urlencoded` и телом:

```text
action=LOGIN&token=GGGGGGGGGGGGGGGGGGGGGGGGGGGGGGGG
```

**Ожидается:** токен проходит валидацию; вызывается `/auth` с тем же токеном; после успешного внешнего ответа приложение возвращает `result: OK` и сохраняет авторизацию. HTTP 200 для успеха — допущение A1.

**Фактически:** HTTP 400 / ERROR; `/auth` не вызывается. Сообщение указывает на ограничение `^[0-9A-F]{32}$`. Такие же отказы воспроизводятся для `Z` × 32 и `ABCDEFGHIJKLMNOPQRSTUVWXYZ012345`; токены из A-F и цифр проходят.

**Автотест:** `TokenValidationIT.acceptsTokensFromRequiredAlphabet`. Семь параметров, три ожидаемых падения на предоставленной версии. В Allure — отдельная категория NC-001, запрос/ответ, внешний журнал и лог приложения.

**Воспроизведение:**

```powershell
.\mvnw.cmd clean verify "-Dit.test=TokenValidationIT#acceptsTokensFromRequiredAlphabet"
```

Не изменять ожидаемый алфавит на A-F и не отключать эти параметры ради успешной сборки.

## O-001 — внешний ответ 301 без Location приводит к успеху

При исследовательском запросе LOGIN с внешним HTTP 301 без заголовка Location приложение ответило HTTP 200 / OK и затем разрешило ACTION. В задании не перечислено, какие внешние коды считаются успешными.

Это наблюдение, а не доказанное нарушение явного требования. Допущение A2 для автоматизированных положительных проверок ограничено представителями 2xx; поведение 3xx не объявлено корректным только по факту наблюдения.

## O-002 — неподдерживаемые метод и тип тела дают HTTP 500

В локальном исследовании GET `/endpoint` с корректным API-ключом и POST с `Content-Type: application/json` возвращали HTTP 500 и JSON `ERROR / Internal Server Error`.

В задании предусмотрен POST с form-urlencoded; ожидаемые коды для других методов и Content-Type не определены. Это кандидаты на улучшение обработки ошибок протокола; ожидаемые 405/415 не приписываются исходной спецификации. Эти наблюдения не используются как основание для тестов, которые закрепляют HTTP 500 как требуемое поведение.
